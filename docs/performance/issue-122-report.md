# Issue #122：版本改造前后性能对照实验

## 1. 结论

在实际部署主机上，以并发数 32、单次 30 秒、每个接口预热 10 秒、每组 3 轮进行测试后：

| 接口 | 指标 | 改造前 `4d3f470` | 当前 `e2b9bbc` | 变化 |
| --- | ---: | ---: | ---: | ---: |
| 酒店目的地 | 吞吐量 | 6415.05 RPS | 6322.31 RPS | -1.45% |
|  | 平均响应时间 | 4.99 ms | 5.06 ms | +1.48% |
|  | P95 | 9.22 ms | 9.41 ms | +2.06% |
| 酒店搜索 | 吞吐量 | 1236.65 RPS | 2926.43 RPS | **+136.64%** |
|  | 平均响应时间 | 25.86 ms | 10.93 ms | **-57.73%** |
|  | P95 | 33.60 ms | 17.43 ms | **-48.12%** |
| 酒店详情 | 吞吐量 | 6202.58 RPS | 9232.64 RPS | **+48.85%** |
|  | 平均响应时间 | 5.16 ms | 3.46 ms | **-32.81%** |
|  | P95 | 8.32 ms | 5.52 ms | **-33.63%** |

两侧 18 次记录共完成 2,910,714 次请求，HTTP/连接错误均为 0，错误率均为 0%。
酒店目的地接口约 1%～2% 的差异处在三轮自然波动范围内，应视为基本持平；酒店搜索和详情接口的提升在三轮中均稳定出现。

## 2. 对照版本

- 改造前基线：Git 标签 `monolith-start` 解引用后的完整提交
  `4d3f470db5fb9a8d4366950fe42943f90bb69584`。
- 当前版本：实验开始时最新远端 `main`
  `e2b9bbc65f163fa7e29ffb2587fc88cfec0e884d`。

标签名称容易造成误解：`monolith-start` 对应的源码已经包含 Gateway、Eureka Discovery、
Hotel、Transport、Reservation、Payment 等独立服务。当前版本则将 Hotel + Transport 合并为
`travel-core-service`，将 Reservation + Payment 合并为 `order-service`。因此本文使用“改造前”与
“当前”命名；这不是严格意义上单体应用与微服务应用的二元对照。

## 3. 测试条件

- 在同一台实际部署主机上顺序运行两个版本，生产工作负载在两侧测试期间均保持运行。
- 主机为 Linux、24 个逻辑 CPU、约 244 GiB 内存；Docker Engine 29.2.1，Docker Compose 5.0.2。
- 两侧均从完整 commit SHA 建立干净的 detached Git worktree 并重新构建镜像。
- 实验栈使用独立 Compose project、独立数据目录和非生产入口，未向生产 K3s Ingress 发送压测流量。
- 两个实验栈轮流运行，不同时争用实验资源；每次退出只清理该实验栈。
- 两侧应用与基础设施容器共享相同的 8 个 CPU 核；压测器固定使用另外 4 个核。
- 三个接口使用相同请求参数、相同顺序、相同并发数、相同预热和持续时间。
- 压测器在每个 worker 内复用 HTTP 连接，并完整读取响应体。

### 接口

1. `GET /hotels/destinations`
2. `GET /hotels/search`，固定目的地、入住/离店日期、2 位成人，按价格排序
3. `GET /hotels/{hotelId}`，使用搜索结果中的同一家酒店和相同日期、人数

未选择 Transport 接口，因为两个提交间的 Transport 种子文件发生过变化，无法直接满足“同一批数据”。

## 4. CPU 与内存

Docker CPU 百分比为多核累计值，例如 600% 约等于持续占用 6 个 CPU 核。下表为 Gateway、
Discovery、目标业务服务、PostgreSQL 和 RabbitMQ 的合计采样均值；闲置但属于目标版本的业务服务
也计入总量。

| 接口 | 版本 | 平均 CPU | 平均内存 |
| --- | --- | ---: | ---: |
| 酒店目的地 | 改造前 | 590.07% | 3152.73 MiB |
|  | 当前 | 605.52% | 2931.93 MiB |
| 酒店搜索 | 改造前 | 591.92% | 3009.35 MiB |
|  | 当前 | 612.05% | 2792.97 MiB |
| 酒店详情 | 改造前 | 606.25% | 3019.97 MiB |
|  | 当前 | 606.79% | 2799.64 MiB |

当前版本在三组测试中的平均内存均低约 7%。主要结构性解释是 Hotel 与 Transport 合并后减少了
一个独立 JVM；CPU 总量相近，而搜索和详情吞吐量更高，说明这两个场景下单位请求的 CPU 成本下降。

## 5. 解释边界

结果可以证明当前提交在本次固定环境、数据和并发条件下，酒店搜索与详情性能更好；不能仅凭本次
实验把全部提升归因于“服务合并”。两个提交之间还包含数据库迁移、金额类型、启动/种子加载、
安全校验和依赖配置等改动。酒店查询使用的主要 Repository 查询及数据库索引基本一致，但尚未通过
Profiler 将提升定位到某个具体函数或 SQL 执行计划。

此外，本实验固定并发数为 32，只代表一个负载点。若要得出容量上限或拐点结论，还应追加阶梯并发
（例如 8、16、32、64、128）和更长时间的稳定性测试。
