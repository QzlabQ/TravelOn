01 / 背景与目标

目标不是单点订票，而是降低出行决策成本

行前规划 - 预订 - 订单 - 分享
酒店搜索与推荐
火车票查询与预订
搜索分散

酒店、火车票、机票和景点信息分散，用户需要多次切换页面和条件。

规划割裂

行程安排、地图路线和票务住宿缺少统一规划入口。

预订链路不连贯

推荐结果如果不能跳转到预订页，用户还要重新检索。

产品目标

用一个入口串起出行基础信息、AI 行程生成、地图点位、酒店/票务推荐、订单管理和社区发布，形成课程验收可展示的完整链路。

核心判断：围绕用户旅程组织功能，而不是按页面堆功能

03 / 用户旅程闭环

四步形成可演示的业务闭环

从 AI 计划到社区内容
1

行前规划

填写城市、日期、人数和偏好，AI 生成 Markdown 行程、地图点位和推荐选项。

2

预订联动

酒店、火车票、机票推荐携带预约链接，跳转到对应预订页面并预填条件。

3

订单管理

用户可查看订单列表、详情、支付状态、取消退款和旅行时间线。

4

行后分享

AI 生成的 Markdown 行程可转发为社区富文本帖子，沉淀为游记内容。

验收视角

演示时可以从 `/ai-planner` 开始，完成一次规划，点击推荐预订入口，再将行程转发到社区，覆盖主要业务链路。

闭环比单点功能更能体现系统完整性

06 / 总体架构设计

微服务架构通过网关统一入口，AI 规划独立演进

React + Spring Cloud + Python Agent

设计要点

  • 前端只访问 API Gateway，降低页面对服务地址的耦合。
  • 业务服务通过 Eureka 注册发现，PostgreSQL 按服务拆分数据库。
  • AI Java 服务保存会话和快照，Python Agent 专注规划执行。
  • WebSocket 承载 AI 流式状态，提升等待过程可解释性。
设计原则：服务边界明确，统一入口，AI 与业务数据解耦
07 / AI 规划设计

AI 模块承担“理解需求、组织行程、联动预订”的中枢角色

悬浮助手 + Markdown + 快照
悬浮助手与生成过程
Markdown、地图和推荐结果
基础槽位

出发城市、目的地、日期、人数、偏好构成规划输入。

结构化结果

places、routes、bookingLinks 驱动推荐卡和预订跳转。

版本设计

手动编辑通过 baseVersion 保存为新快照，避免覆盖 AI 结果。

交互设计

把 AI 操作从主工作区收束到悬浮窗，主区专注 Markdown、地图和推荐结果。

AI 规划不是聊天框，而是行程方案生产和业务入口编排器
08 / 数据与服务设计

不同数据用不同存储，降低业务耦合

PostgreSQL / MongoDB / RabbitMQ
首页与统一入口
账户与基础资料
订单管理
社区与内容沉淀

PostgreSQL

  • 承载酒店、交通、用户、订单、支付、社区等业务数据。
  • 按服务拆分数据库，表结构通过初始化脚本维护。
  • 适合强结构、可查询、可验证的交易数据。

MongoDB

  • 保存 AI 规划会话、消息、Planner Snapshot。
  • 适合半结构化规划结果和版本历史。
  • 支撑历史回看、回滚、手动 Markdown 新版本。

Gateway / RabbitMQ

  • Gateway 统一 HTTP 与 WebSocket 入口。
  • RabbitMQ 支持部分服务间消息协作。
  • Eureka 提供服务注册发现，便于容器化部署。

数据设计结论

业务订单和产品数据需要稳定约束，放在 PostgreSQL；AI 规划结果变化快、结构丰富，放在 MongoDB；跨服务入口和通信由 Gateway、Eureka、RabbitMQ 处理。

分层存储让 AI 迭代不影响核心交易数据
09 / 关键设计取舍

当前实现优先保证演示闭环稳定、边界清晰

Pragmatic Design Choices
1

统一入口

前端不直接调用各服务，统一走 Gateway，后续替换服务地址或容器部署不影响页面。

2

AI 服务解耦

Java 负责协议、版本和持久化；Python Agent 负责模型和工具编排，职责分离。

3

快照防覆盖

AI 返回、用户手动编辑、历史版本切换都进入版本体系，避免状态被静默覆盖。

4

真实接口优先

酒店、票务、景点推荐优先走业务接口或 AMAP 数据，失败时明确 warning，不回退到伪链接。

取舍标准：能解释、能演示、能继续迭代
