01 / 背景与目标

面向全旅程场景的一体化出行旅游平台

行前规划 - 行中服务 - 行后分享

为满足用户日益增长的出行与旅游预订需求，TravelOn 需要建设一款集机票预订、酒店住宿、旅游度假、火车票购买于一体的综合出行旅游平台。平台提供丰富的出行产品选择、智能的行程规划工具、透明的价格信息与便捷的预订流程，覆盖用户“行前规划 - 行中服务 - 行后分享”的全旅程场景。

搜索分散

酒店、火车票、机票和景点信息分散，用户需要多次切换页面和条件。

规划割裂

行程安排、地图路线和票务住宿缺少统一规划入口。

预订链路断点

推荐结果若不能跳转预订页，用户仍需重复检索和确认条件。

产品目标

串联基础信息、AI 行程、地图点位、酒店/票务推荐、订单管理和社区发布，形成完整业务闭环。

酒店搜索与推荐
火车票查询与预订
业务价值：减少跨平台切换成本，提升规划、预订与内容沉淀的一致性

06 / 总体架构设计

微服务架构通过网关统一入口，AI 规划独立演进

React + Spring Cloud + Python Agent

入口层

React 前端统一通过 API Gateway 访问后端能力，页面不直接绑定各微服务地址。网关同时承载 HTTP 请求和 AI 规划 WebSocket 流式通道，使普通业务操作与 AI 生成状态都能从统一入口进入系统。

业务服务层

酒店、交通、预订、社区、用户与支付服务按业务边界拆分，通过 Eureka 完成服务发现。各服务负责自身领域模型和接口，避免订单、票务、社区内容互相侵入。

AI 编排层

AI Java 服务负责会话、消息、快照版本和 WebSocket 状态同步；Python Agent 负责模型调用、工具编排、AMAP/票务/酒店数据查询与结构化结果生成。

数据与协作层

PostgreSQL 承载稳定业务数据，MongoDB 保存 AI 会话与半结构化快照，RabbitMQ 支持部分服务间消息协作。该设计保证核心交易数据稳定，同时允许 AI 模块快速迭代。

设计原则：服务边界明确，统一入口，AI 与业务数据解耦

08 / 数据与服务设计

不同数据用不同存储，降低业务耦合

PostgreSQL / MongoDB / RabbitMQ
首页与统一入口
账户与基础资料
订单管理
社区与内容沉淀

PostgreSQL

  • 承载酒店、交通、用户、订单、支付、社区等业务数据。
  • 按服务拆分数据库，表结构通过初始化脚本维护。
  • 适合强结构、可查询、可验证的交易数据。

MongoDB

  • 保存 AI 规划会话、消息、Planner Snapshot。
  • 适合半结构化规划结果和版本历史。
  • 支撑历史回看、回滚、手动 Markdown 新版本。

Gateway / RabbitMQ

  • Gateway 统一 HTTP 与 WebSocket 入口。
  • RabbitMQ 支持部分服务间消息协作。
  • Eureka 提供服务注册发现，便于容器化部署。

数据设计结论

业务订单和产品数据需要稳定约束，放在 PostgreSQL；AI 规划结果变化快、结构丰富，放在 MongoDB；跨服务入口和通信由 Gateway、Eureka、RabbitMQ 处理。

分层存储让 AI 迭代不影响核心交易数据
09 / 工程设计结论

当前实现围绕稳定闭环、清晰边界与真实数据优先展开

工程实现原则
1

统一入口

前端不直接调用各服务，统一走 Gateway，后续替换服务地址或容器部署不影响页面。

2

AI 服务解耦

Java 负责协议、版本和持久化；Python Agent 负责模型和工具编排，职责分离。

3

快照防覆盖

AI 返回、用户手动编辑、历史版本切换都进入版本体系，避免状态被静默覆盖。

4

真实接口优先

酒店、票务、景点推荐优先走业务接口或 AMAP 数据，失败时明确 warning，不回退到伪链接。

工程结论：核心链路可解释、可验证，并保留后续模块扩展空间
