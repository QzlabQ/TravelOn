## 5. 容器化部署与运行

### 5.1 容器范围

| 类别 | 组件 | 启动方式 |
|---|---|---|
| 前端 | React/Nginx 前端镜像 | `travel-ui/Dockerfile`，执行 `docker build` 和 `docker run` |
| 后端入口 | Gateway、Eureka Discovery | `travel-api/docker-compose.yml` |
| 业务服务 | hotel、transport、reservation、payment、user、community、AI arrange/agent 等 | `travel-api/docker-compose.yml` |
| 数据与中间件 | PostgreSQL、MongoDB、RabbitMQ | `travel-api/docker-compose.yml` |

后端启动：

```bash
cd travel-api
docker compose up -d --build
docker compose ps
```

前端容器启动：

```bash
cd travel-ui
docker build -t travel-ui .
docker run -d --name travel-ui --restart unless-stopped -p 80:80 travel-ui
```

详细环境变量、端口、数据库初始化、服务发现和业务链路验证步骤见[部署文档](部署文档.md)。

## 6. 自动构建与测试

### 6.1 已完成：本地统一自动化入口

仓库通过 [`mise.toml`](../mise.toml) 和 [`tests/run_tests.py`](../tests/run_tests.py) 提供统一测试入口：

```bash
mise install

mise run test:unit
mise run test:integration
mise run test:e2e
mise run test:all
```

统一入口覆盖 Java 服务测试、Python/Pytest、前端测试、Docker Compose 集成测试和 Playwright 端到端测试；任一模块失败时命令返回非零退出码。历史统一执行结果为 155/155 通过，详见[本地测试与覆盖率结果](testing-results-2026-08-27.md)。

### 6.2 已完成：GitHub Actions CI

仓库中的 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) 已接入 GitHub Actions，触发条件为：

- 向 `main` 提交或更新 Pull Request；
- push 到 `main`；
- 通过 `workflow_dispatch` 手动运行。

流水线自动执行以下步骤：

1. 检出仓库并通过 mise 安装项目工具链和依赖；
2. 编译/打包所有 Java 服务，检查 Python Agent 源码，并构建 React 前端；
3. 构建 `travel-ui` Docker 镜像；
4. 执行 `mise run test:unit` 单元测试；
5. 准备集成环境并执行 `mise run test:integration`；
6. 无论成功或失败均上传 `artifacts/test-results/`，报告保留 14 天。

## 7. 微服务划分、接口与数据归属

### 7.1 微服务划分

[微服务划分图](architecture/architecture-diagram.md)给出了目标架构、现状到目标的变更对照、服务边界依据、关键调用链、网络和端口。划分遵循以下原则：

- 对外 HTTP 路径保持稳定，服务合并只调整内部部署边界；
- 酒店与交通能力归入 travel-core 边界；
- 订单与支付归入 order 边界；
- 用户、社区和 AI 规划因数据与职责独立而保留；
- Gateway 负责统一入口，Eureka 负责服务发现；
- RabbitMQ 用于预订、库存与补偿协作。

该图描述目标划分，当前实际运行基线另见[代码核实基线](architecture/verified-baseline.md)，两者不能混写。

### 7.2 服务接口清单

[服务接口清单](architecture/service-interface-inventory.md)按源码核实并记录：

- Gateway 对外 REST 路径；
- AI 与订单相关 WebSocket；
- 服务间 RabbitMQ 队列、exchange 和 routing key；
- 鉴权方式与关键查询参数；
- 现状、目标和兼容策略；
- 服务合并前后的接口差异及前端影响。

目标架构保持 `/hotels/**`、`/transports/**`、`/reservations/**`、`/users/**`、`/community/**` 和 `/ai-arrange/**` 等外部路径不变，降低前端与部署迁移风险。

### 7.3 数据表归属方案

[数据表归属方案](architecture/database-ownership-plan.md)记录了现状数据库、真实表清单、目标归属、数据访问边界、迁移与回滚方式。核心归属如下：

| 目标服务 | 数据库 | 主要数据 |
|---|---|---|
| travel-core-service | `travel_core_db` | 城市、酒店、房型、房间预订、票务模板与查询视图 |
| order-service | `reservation_db` | 订单、旅客快照、支付流水、退款记录 |
| user-service | `user_db` | 用户与常用旅客 |
| community-service | `community_db` | 帖子、评论、点赞、收藏、评价、景点和路线 |
| ai-arrange-service | MongoDB `ai-arrange-db` | 规划会话、消息、快照和版本 |

当前代码没有跨库直接查询；跨服务协作通过 HTTP 或 RabbitMQ 完成。目标方案继续禁止跨服务数据库外键和直接访问。
