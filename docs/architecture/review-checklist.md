## 二、待确认事项

### 确认项 1：offer-provider 由"合并"改为"删除"

**依据：** `OffersService` 三个方法分别返回 `List.of()`、硬编码占位对象（`hotelName = "旅游产品功能重构中"`、`price = -1.00`）和 `-1.00`；无数据库、无 `rabbitTemplate` 调用、WebSocket 未注册 handler。它没有可合并的逻辑。

- [ ] 同意删除
- [ ] 保留为空壳，理由：______

---

### 确认项 2：对外 HTTP 路径全部不变

`/reservations/**` **不**改名为 `/orders/**`。服务内部叫 `order-service`，对外路径保持原样。

**依据：** 改名会牵动 WebSocket 路径 `/reservations/ws/offerBought`、Gateway 路由顺序与前端调用，收益为零。

- [ ] 同意保持不变
- [ ] 要求改名，接受前端联动改动

---

### 确认项 3：order-service 沿用 `reservation_db` 库名

**依据：** 订单与支付数据已全部在该库中。改名需要一次 `pg_dump` + restore + 停机，只换来名字好看。

- [ ] 同意沿用（服务名与库名不一致，在 README 注明）
- [ ] 要求改名为 `order_db`，接受停机迁移

---

### 确认项 4：travel-core 新建 `travel_core_db`

hotel 与 transport 的表当前分处两库，必须物理合并到一个库，否则单进程需配置双数据源。

seed 由 Flyway 从 CSV 重建，**不需要 `pg_dump` 导数据**。但 init 脚本只在**空数据卷**首次启动时执行。

- [ ] 开发环境重建数据卷（`rm -rf travel-api/data/postgres`）
- [ ] 手工建库 + 执行 schema，保留现有数据卷

### 3.2 风险

| 风险 | 概率 | 影响 | 应对 | 评审意见 |
|------|------|------|------|---------|
| 队列绑定遗漏致 RPC 超时 | 中 | 高 | 比对 RabbitMQ binding 列表 | |
| 支付补偿路径被误删 | 低 | 高 | 强制 Code Review + 失败场景实测 | |
| `city` seed 重复致行数翻倍 | 低 | 中 | 行数校验 | |
| 前端依赖 `/offers/` 未发现 | 中 | 中 | 阶段 0 先确认 | |
| Gateway 路由顺序错误致 WS 失败 | 中 | 中 | WebSocket 场景测试 | |
| 已有数据卷不执行 init 脚本 | 高 | 中 | 重建数据卷或手工建库 | |

**最高风险是前两项。** 队列绑定问题在于 `hotels.requests.checkAvailabilityByQuery.exchange` 上存在**两条**不同 routing key 的绑定（hotel 侧用队列名、reservation 侧用 `...routingKey`），合并时只删其一会导致可用性查询静默超时。
