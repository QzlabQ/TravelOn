需求来源

原始目标到可验收范围

从“大而全”收敛到“可演示闭环”

原始目标

建设集机票预订、酒店住宿、旅游度假、火车票购买于一体的综合出行旅游平台。

场景边界

覆盖用户“行前规划 - 行中服务 - 行后分享”的全旅程。

当前交付

以课程演示为目标，完成账户、查询、订单支付、社区、AI 规划、部署与测试文档。

需求收敛原则：先保证核心业务链路可跑通，再把价格趋势、真实第三方接口、复杂运营后台作为后续增强项。

需求来源：需求.txt 与 docs/需求规格.md2 / 14

设计支撑

为什么这些需求能被实现

前端展示层

React + TypeScript + MUI，提供账户、查询、订单、社区和 AI 规划页面。

网关与微服务层

API Gateway 统一入口，Eureka 服务发现，业务拆分为 hotel、transport、reservation、payment、user、community。

数据与智能层

PostgreSQL 保存业务数据，MongoDB 保存 AI 会话与快照，RabbitMQ 支持服务间解耦。

需求类型设计落点好处
查询与预订酒店、交通、订单、支付服务服务边界清晰，便于独立测试
AI 规划ai-arrange-service + ai-arrange-agent-service规划能力与普通业务解耦
部署验收Docker Compose + Gateway + Eureka可复现、可检查、可课堂演示
设计文档：docs/概要设计.md、docs/详细设计.md11 / 14

风险与边界

当前完成中的限制说明

限制项影响当前处理
AI 依赖外部模型 Key未配置时不能保证真实生成质量页面和会话功能可展示，并提供错误提示或 fallback 说明
真实票源接口未接入不能完成真实出票使用模拟数据完成课程级搜索、下单和支付闭环
完整后台管理未完成运营侧能力不完整通过 seed 数据、前台功能和文档完成本次验收
部署截图仍可补充部署文档视觉证据不足测试文档已有页面截图，部署状态截图可后续补齐

这些限制不改变 P0 核心流程已完成的结论，但展示时需要主动说明边界，避免把模拟演示说成真实商业系统。
